# AI-Native 读书雷达｜优先级规划方案（依赖优先版）

面向：非技术背景 PM / 业务负责人  
目标：在不引入复杂账号体系的前提下，让产品从“可演示原型”升级为“可运营的共建雷达”，并明确每一步依赖关系与落地顺序。  
当前技术基线：当前仓库仍是已验证能力参考库，但后续前端主基线改为“当前主版本”；MVP 阶段后端正式采用 Supabase（底层为 PostgreSQL）快速搭建，前端继续承接品牌化雷达体验。

---

## 0. 我们已经确认的关键结论（作为本规划的硬前提）

- 前端主基线不再以当前版本继续扩展，而是切换为“当前主版本”为主；当前版本保留为能力参考库，用于迁移推荐、测试保护网、已有业务规则。
- 选择当前主版本的原因已明确：它在当前阶段的主要优势是“代码更稳、布局更合理”，更适合作为后续正式 Demo 的承接底座。
- 冷启动阶段不采用伪数据兜榜单；当真实数据不足时，对应卡片不显示，避免制造虚假的“热度感”。
- 邀请码机制已确定采用统一邀请码：无需账号系统，只需在弹窗填写邀请码1234，任何人都可以推荐。
- 雷达点位希望直接展示书籍缩略图，当前已确定为“每个领域展示 4-5 本重点书”，以强化重点可读性；后续仍需控制整体视觉噪音。
- 后端方案正式采用 Supabase 作为 MVP 快速搭建方案；目标是优先解决共享数据、推荐入库、审核闭环。
- iCloud 风格只借鉴“气泡轮转/漂浮/高亮节奏”的动效语言，且主要体现在“重点书缩略图气泡”上；这些气泡以雷达原始位置为中心做小范围漂浮与轮流高亮，不照搬整套视觉皮肤，避免和公司品牌风格冲突。
- 搜索当前阶段暂不纳入实施范围，先优先完成主基线切换、内容地基、推荐闭环与重点书气泡效果。

## 1. 依赖优先原则（为什么要先做被依赖项）

为了避免“做了很多 UI，最后因为数据/规则没定导致推倒重来”，本规划采用三条依赖优先原则：

1) 先定“主基线版本”，再做增量开发与视觉强化  
2) 先定“内容源与字段映射”，再做“展示形态”  
3) 先定推荐journey，再做“评分算法/榜单算法”  
4) 先做“可配置与可运营”，再做“复杂自动化与智能化”

你可以把它理解为：先确定“用哪间监控室”（主基线版本），再接好“电力和线路（数据/规则）”，最后再升级“屏幕与仪表盘（UI/动效）”。

## 2. 功能项依赖关系总览（先解决被依赖项）

下表只写“关键依赖”，便于决策与排期。

| 功能项（业务描述） | 价值一句话 | 关键依赖（必须先完成） | 可用冷启动方案 | 主要风险 |
|---|---|---|---|---|
| 切换到当前主版本作为前端主基线 | 避免在次优基线上继续加需求，降低后续返工 | 明确当前主版本将作为正式承接版本 | 先按口头确认推进规划，待代码接入后做差异盘点 | 若未做能力盘点，可能丢失当前已验证能力 |
| Excel 真实书单导入（作为系统内容源） | 解决“上线无内容”的硬问题 | 统一字段映射与最小数据模型 | Excel → JSON（静态导入） | 字段不一致导致后续渲染异常 |
| 榜单卡片（本周上新/本月最火/观看最多/Top10） | 给用户“快速入口”，提升留存 | 内容源（书单/ID） | 数据不足时不展示对应卡片 | 若无口径说明，容易被质疑“最火如何计算” |
| 每页都放“推荐入口” | 提升共建提交率 | 无（直接做 UI 即可） | 全局浮动入口/顶部入口 | 入口过多造成打扰 |
| 筛选栏隐藏/折叠（最大化雷达） | 强化“雷达主视觉” | 无（纯 UI 结构调整） | 默认折叠 + 悬浮唤出 | 新用户可能找不到筛选 |
| 雷达点位显示缩略图（限量） | 让用户一眼识别重点书 | 内容源必须有封面字段；TopN 规则 | 每个领域展示 4-5 本重点书，其余圆点 | 视觉噪音、性能、遮挡 |
| 悬停高亮 + 简要信息（Tooltip） | 降低点击成本，提高探索效率 | 点位数据字段齐全 | 仅展示书名/推荐指数/推荐理由摘要 | 信息过多反而干扰 |
| 口径不清引发争议 |
| Supabase + 数据库 + 审核流 | 从“单机”变“可运营系统”，并快速建立共享数据底座 | 数据模型、运营口径、最小权限策略 | 采用 Supabase 承接 MVP 阶段正式后端能力 | 若直接把业务逻辑过度绑在平台特性上，未来迁移成本上升 |
| 评分算法/雷达显示算法 | 让雷达“会演化” | 有足够的真实行为数据（点击/评分/推荐） | 初期用运营配置兜底 | 算法不可解释会损害信任 |
| iCloud 式气泡轮转（重点书缩略图气泡） | 提升演示吸引力，让主视觉更有生命力 | 主基线确定、品牌风格边界明确、重点书点位与雷达结构稳定 | 以雷达原始位置为中心，对重点书缩略图气泡做小范围漂浮与轮流高亮 | 若动效过重，可能压过雷达判断效率 |
| 公司调性 UI + 对应 MD 文档 | 统一风格，便于对外协作 | 设计规范确认（色板/字号/圆角） | 从现有 Tailwind 变量出发 | 大改导致回归风险 |

## 3. 可落地的分阶段执行方案（按依赖排序）

### Phase 0（先把“内容与运营开关”做出来）— 冷启动可运营
目标：不引入后端也能“看起来像在运营”，且内容可持续更新。

#### 0.0 切换前端主基线：以当前主版本为主，当前版本为能力参考
- 用户可见结果：后续所有 Demo 与正式前端迭代都建立在“更稳、更合理的当前主版本”上，而不是继续在当前版本上叠加修改。
- 已确认原因：
  - 当前主版本在当前阶段的主要优势是“代码更稳、布局更合理”。
  - 当前版本仍有价值，但它更适合作为“能力资产库”，用于迁移已验证能力，而不是继续做正式承接底座。
- 当前版本建议保留的参考资产：
  - 推荐抽屉与 URL Query 控制思路
  - 本地推荐历史与表单校验逻辑
  - 已补好的测试保护网
  - 业务规则与已有文档
- 验收标准：
  - 当前主版本被明确写入为主基线。
  - 当前版本与当前主版本形成“主基线 / 能力参考库”的关系，而不是并行双版本长期维护。

#### 0.1 统一 Excel 字段映射
- 用户可见结果：上线即有真实书单、字段展示一致，后续所有 UI/榜单都能复用。
- 输入数据（你提供/运营维护的 Excel 字段）：context/AI-Native读书雷达·资料共建.xlsx
  - 资料名称、资料类型、资料链接、能力主题、推荐程度、推荐理由、推荐人全部存到对应的supabase


#### 0.2 榜单卡片（真实数据驱动，数据不足不展示）
- 用户可见结果：首页只展示当前已有真实数据支撑的榜单入口；数据不足的卡片直接不显示，不用伪数据补位。
- 冷启动口径（对外解释方式）：
  - 本周上新：仅在已有真实新增内容时展示
  - Inspire Top 10：仅在内容量和排序依据足够时展示
  - 观看最多/本月最火：仅在已有真实行为数据时展示
- 验收标准：
  - 页面不会为了“看起来完整”而硬凑榜单卡片。
  - 用户看到的每一张榜单卡片都有真实数据依据。

#### 0.3 全局推荐入口（每页可见但不打扰）
- 用户可见结果：无论在首页还是其他页，都能一键打开“推荐一本书”的抽屉。
- 推荐的呈现方式（避免打扰）：
  - 桌面端：右下角小浮动按钮（不遮挡内容）
  - 移动端：底部轻量按钮或导航入口
- 验收标准：
  - 入口统一、不会在页面内出现多个重复 CTA。

#### 0.4 筛选栏折叠（最大化雷达）
- 用户可见结果：默认雷达更大；需要筛选时一键唤出；收起后仍能看到“当前筛选摘要”。
- 验收标准：
  - 新用户能发现筛选（有明显图标/文案提示）；老用户能高效折叠/展开。

#### 0.5 公司调性 UI + 文档（MD）：context/MASTER.md
- 用户可见结果：整体视觉统一，团队协作有“设计护栏”。
- 输出：一份 MD（色板、字号、间距、卡片圆角、组件用法示例）。
- 验收标准：
  - 新页面照着 MD 写，不会跑偏。

---



#### 1.1 悬停高亮 + 简要信息卡（Tooltip 升级）
- 用户可见结果：鼠标移动到点位时，高亮点位并弹出简要信息（书名/推荐指数/一句理由）。
- 验收标准：
  - 信息不超过 3 行；不遮挡核心区域；移动端采用点击触发。

#### 1.2 点位缩略图（限量 TopN 的混合模式）
- 用户可见结果：每个领域/扇区有少量“封面点”，其余保持彩色圆点，雷达干净但有重点锚点。
- 限量规则（已确认）：
  - 每个领域展示 4-5 本重点书（按推荐指数或编辑精选标记），其余内容仍使用普通点位。
- 验收标准：
  - 点位不拥挤；封面可辨识；无封面时自动降级为纯色点。



#### 1.5 重点书气泡动效规则（iCloud 风格的落地方式）
- 参考https://www.icloud.com/ 的 <div class="exploreradar aem-GridColumn aem-GridColumn--default--12">
- 参考 http://thoughtworks.com/radar
- 用户可见结果：重点书缩略图像气泡一样轻微漂浮、轮流高亮，页面更有生命力，但仍然看得懂雷达结构。
- 规则（已确认方向）：
  - 只作用于“每个领域 4-5 本重点书”的缩略图气泡，普通点位不参与该动效。
  - 每个气泡都以自己的原始雷达位置为中心，只做小范围漂浮，不脱离所属领域和圈层。
  - 系统按固定节奏轮流高亮重点书；高亮状态接近 hover，但略弱于用户主动悬停。
  - 当用户鼠标移入、悬停或点击某个点位时，自动高亮应暂停，让交互优先。
  - 不做自由乱飞，不做高频跳动，不做大范围位移。
- 验收标准：
  - 动效增强演示感，但不影响读图、判断和点击交互。

### Phase 2（引入后端与审核，形成真实共建闭环）— 从 Demo 到产品

后端设计为context/DATAschema&backend-design.md
目标：让推荐数据跨端可用、可审核、可追溯；让榜单在真实数据足够时逐步出现，而不是先用伪数据填满页面。

#### 2.1 Supabase + 数据库 + 最小后端能力
- 用户可见结果：推荐记录不再丢失；换电脑也能看到；运营能统一管理；团队能更快把“在线共享 MVP”跑起来。
- 当前决策：
  - MVP 阶段正式采用 Supabase。
  - 采用它的原因不是长期偷懒，而是为了用最快速度建立共享数据库、推荐入库、审核闭环。

## 6. 优先级矩阵（依赖优先版）

说明：这里的“优先级”不是单纯按价值排序，而是按“被依赖程度 + 价值 + 成本 + 风险”综合排序。

| 象限 | 定义 | 功能项 | 结论 |
|---|---|---|---|
| A1（先做地基） | 高依赖 + 高价值 | 主基线切换、统一字段映射/Excel 导入、Supabase 数据模型、榜单展示门槛、邀请码规则定义 | 第一批必须完成，否则后续做啥都容易返工 |
| A2（先做体验杠杆） | 低依赖 + 高价值 | 推荐入口全局化、筛选折叠、Tooltip 升级 | 第二批完成，立刻提升用户可感知体验 |
| B1（可控增强） | 中依赖 + 中高价值 | TopN 缩略图点位、推荐打分+加权展示、iCloud 式气泡轮转 | 在地基稳定后做，避免视觉噪音与口径不清，并确保动效不破坏雷达原始判断结构 |
| C（后做系统化） | 高成本 + 高不确定 | 审核后台深化、算法化热度、雷达显示算法 | 作为 2.0 战役，前期用运营配置兜底 |

## 8. 协作说明（非技术版）

### 8.1 现在已经拍板的事

- 后续前端不再以当前版本为主继续加功能，而是以“当前主版本”为主基线。
- 当前版本不会废弃，它保留为“能力参考库”，主要提供：
  - 推荐抽屉思路
  - 已跑通的推荐表单与历史记录逻辑
  - 已补好的测试保护网
  - 已确认的业务规则与规划文档
- 后端在 MVP 阶段正式采用 Supabase，目标是先把“多人共享、推荐入库、审核闭环”跑通。
- 视觉上不照搬 iCloud，只借它“重点书气泡轻微漂浮、轮流高亮”的动态感觉，而且这些气泡仍然以雷达原始位置为基础，不是纯装饰背景。

### 8.2 为什么现在先用当前主版本

- 之所以选当前主版本，是因为它当前更适合做主承接底座：
  - 代码更稳
  - 布局更合理
  - 更适合继续叠加后续功能和品牌化表达
- 当前版本的价值在于“有几块已经验证过的能力”，这些能力后续按需迁入，而不是整个版本继续扩展。

### 8.3 现在最重要的不是把界面继续做花，而是先统一地基

- 先统一 3 件事：
  1. 用哪个前端版本继续做  
  2. 系统内部的数据字段长什么样  
  3. 推荐、邀请码、榜单这些规则怎么定
- 这 3 件事没统一，后面 UI 和后端都会返工。

### 8.4 这份规划里已经确定的业务规则

- 邀请码采用“提权模式”
  - 任何人都能推荐
  - 有邀请码的人推荐权重更高
  - 不做“无邀请码不能提交”的门禁模式
- 雷达重点书展示规则
  - 每个领域展示 4-5 本重点书封面
  - 其他内容仍然保持普通点位
- iCloud 式动效规则
  - 动效作用在重点书缩略图气泡上
  - 气泡以原始雷达位置为中心做小范围漂浮
  - 系统可轮流高亮其中一部分重点书
  - 不能把气泡做成脱离雷达逻辑的自由乱飞效果
- 榜单冷启动口径
  - 当前不采用伪数据或编辑精选兜底
  - 数据不足时，对应榜单卡片不显示

### 8.5 主版本接手时，建议先看什么

- 先看整体结构：页面布局、模块分区、组件复用方式
- 再看数据入口：现在数据从哪里来，后面怎么接 Excel / Supabase
- 再看哪些地方适合接入下面这些能力：
  - 推荐入口
  - 推荐抽屉
  - 榜单区
  - Tooltip
  - 雷达重点书封面点位

## 9. 可执行计划（给 PM 和执行同学共用）

### 9.1 第一阶段：切基线、做盘点

目标：先把“在哪个版本上继续做”彻底定住。

- 任务 1：确认当前主版本为主基线
- 任务 2：对当前版本做能力盘点
- 任务 3：形成迁移清单

- 后续主版本是谁
- 当前版本哪些能力必须迁过去
- 哪些能力可以不迁

### 9.2 第二阶段：统一内容与规则

目标：把后面所有页面、榜单、雷达点位都会用到的数据地基统一好。

- 任务 4：统一 Excel / CSV 字段映射
- 任务 5：定义系统内部字段模型
- 任务 6：确定榜单展示门槛
- 任务 7：把邀请码、推荐打分、数据不足不展示榜单这些业务规则写死到文档中

- 一条书单数据进入系统后长什么样
- 一条推荐数据进入系统后长什么样
- 榜单展示门槛、邀请码、重点书展示依据是什么

### 9.3 第三阶段：先做前端可见成果

目标：不等后端全部建完，先把能直接增强体验的内容做出来。

- 任务 8：全局推荐入口
- 任务 9：筛选栏折叠
- 任务 10：公司调性 UI 统一
- 任务 11：Tooltip 升级

这一阶段完成后，用户应该直接感知到：

- 页面更统一
- 雷达更聚焦
- 内容重点更好理解
- 推荐入口更容易发现

### 9.4 第四阶段：接 Supabase，跑通共建闭环

目标：把“本地演示”变成“多人共享的在线 MVP”。

- 任务 13：建立 Supabase 数据表
- 任务 14：接入正式内容库
- 任务 15：接入推荐记录表
- 任务 16：接入邀请码与审核状态

这一阶段完成后，用户应该直接感知到：

- 推荐不再只存在本地
- 换设备也能看到统一内容
- 平台开始具备真正的共建能力

### 9.5 第五阶段：做增强项，不抢主流程

目标：在不破坏专业感的前提下，增加演示吸引力。

- 任务 18：重点书缩略图气泡接入 iCloud 式漂浮与轮流高亮
- 任务 19：榜单在真实数据足够时逐步开放
- 任务 20：继续优化审核后台与内容治理

这一阶段的原则只有一句：

- 所有增强项都不能压过“看懂雷达、理解内容、完成推荐”这条主路径

## 10. 第一轮实施建议（谁先做什么）

如果马上要开始做，我建议第一轮只做下面 4 件事：

### 第一轮优先做

1. 当前主版本能力盘点  
2. Excel 字段映射统一  
3. 榜单展示门槛确认  
4. 全局推荐入口与筛选折叠

### 第一轮暂时不做

- 不先做复杂审核后台
- 不先做真实热度算法
- 不先做完整气泡动效实现
- 不先做复杂权限体系

### 原因

- 这 4 件事最像“地基 + 第一层可见成果”
- 做完之后，团队既能继续推进 UI，也能顺势接 Supabase
- 如果一开始就先做审核、算法、动效，很容易分散注意力
